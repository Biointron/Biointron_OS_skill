# RushData Order Design

Use customer-provided project data and design files to complete the authorized order workflow. Calling `submit/batch` submits selected orders for human confirmation; production begins only after Biointron's confirmation. It is not payment or evidence of production or experimental completion.

## Conversation Language

Choose `language="zh"` or `language="en"` from the customer's natural-language instructions and retain it in the client conversation. Chinese instructions use Chinese and English instructions use English; follow a clear later language change. Keywords such as `CD2`, SKUs, paths, credentials, numbers and short selections do not change the language. Pass `language` explicitly to the `order_design` prompt and every order MCP tool; standalone CLI uses `--language zh` or `--language en`. Omitted language defaults to `zh` for existing callers only. The server does not remember a global language between requests.

Use the selected language for all customer-visible explanations, package copy, questions, choices, help, validation/errors, catalog summaries/navigation and progress messages. Use the selected-language fixed copy verbatim: an instruction to preserve wording never means forcing Chinese into an English conversation. The language of this Skill or its references is not the customer's language. Keep API keys/enums, assay identifiers, brands, user data, product identifiers, credentials and signed context unchanged. Keep `language` outside `data`, `supplied`, upstream business payloads and `workflow_context`; retain it in the outer client handoff record. Preserve raw backend messages as evidence and explain their meaning to the customer in the chosen language.

## Opening and Collection

Use progressive loading. The default MCP `order_design` prompt contains only package introductions and the first question. If current entry instructions already contain the package copy, immediately present it and invoke the native package selector without an extra prompt or input-tool call. Do not read this entire Skill, both references, connection configuration or service versions before that first question. Prefer MCP tools for normal execution.

`get_order_input_requirements(stage, supplied=None, language="zh", detail="compact", mode="collect")` defaults to collection only. It returns `status=collecting|collected`, `validation_deferred=true`, `write_performed=false`, and a batch of independent questions. `collected` means the known branch has been collected, not that input is valid or a write is authorized. Ask routing decisions (package, Customized sample form, antigen source) separately before their dependent fields. Then invoke the returned `interaction.native_question.questions` in one native call for independent text and choice fields, using the selected language. Merge the whole batch before requesting the next branch or batch; do not call MCP, the model or full validation after every field. CLI prompts through the same batch sequentially without model/MCP round trips, rule rereads or business validation inside the batch. Missing or blank routing answers still need questions. Preserve real `false`, `0` and explicitly supplied `[]`; never invent defaults. Collection does not perform full business validation or scan XLSX contents. Immediately before an actual design or cart write, call `get_order_input_requirements(..., mode="validate", language=language)` with all collected inputs. Validate the whole stage once; on `status=needs_input`, explain all discovered issues and invoke its native correction batch, preserving valid answers. Revalidate after the correction batch, not after each field. `status=ready` confirms local validity only. Compact validation retains all discovered issues and the question batch; use `detail="full"` only when a complete schema or diagnostic report is needed. Actual write-entry guards remain intact: authentication, file transport limits, company eligibility, live catalog and saved-context checks still precede the relevant API call. Keep credentials in client state; account, App Key and JWT never enter `supplied` or business DTOs. Collection and validation do not authorize a write. Reuse the current language, valid JWT and catalog candidates. Do not insert planning, recaps, tool discovery, reconnection or repeated authentication between questions.

Read [business-context.md](references/business-context.md) only for the specific terminology or business explanation needed. Product-library search uses the current tool schema and the local input response's `catalog_auth` credential/connection guidance. Before the first design, cart, quote or submission operation, load `order_design(phase="execute", language=language)` once: its default `detail="compact"` provides concise execution rules and connection metadata. Reuse them for later stages, including existing-order continuation. The full Skill and references remain available through explicit `detail="full"` or the relevant reference section when a concrete issue requires them; do not load both by default. These changes reduce repeated work, but model, network and backend timing do not support a guaranteed number of seconds.

For a new order, first introduce Basic, Standard, Premium and Customized before asking the customer to choose. Use the current entry's short copy to explain sample format, measurements and expected data; detailed `business-context.md` explanations can wait until needed. Do not present four unexplained names or internal catalog codes. Package explanation and local information collection do not require customer credentials. Choosing our product library does: check the current customer's valid JWT or obtain missing Biointron Account/App Key values before asking for a search keyword. External-link and manual modes defer authentication until design submission. All modes verify company eligibility before any design write. If the user explicitly starts as a new customer or asks to forget earlier order information, do not reuse prior credentials, selections or order context; this does not cancel real orders.

Package selection is the first order-data question. If Customized is selected, ask its sample form next as a separate routing decision. Collect its protein-property, binding and developability selections in the next independent-field batch, together with other eligible fields. Every required category needs a real answer, including an explicit no-test choice where allowed. Reuse confirmed choices. At pre-write validation, name all incompatible selections and their reasons, then request a correction batch; never silently remove or replace selections.

Collect the project nickname, antigen count, target, desired data, antigen details and original design file in independent-field batches after their routing choices. **Antibody quantity is not a customer form field or confirmation question.** The public form schema excludes it. Keep the original XLSX for the single non-blocking count of named sample rows during actual design execution. Skip headers, blank rows and known helper sheets (`AI spec`, `_mapping`, `_options`); recognize sample headers including `VH/Protein` only for counting. Normal MCP question routing and write-entry form checks validate filename/Base64/nonempty/size limits without scanning XLSX contents for counts. The actual `start_design` path makes one best-effort count of the original workbook before writing. CLI collection uses the returned question batch without validation or XLSX scans between its fields; any successful execution-time count remains internal. If the template cannot be recognized or multiple sheets make the count uncertain, omit the field and discard stale/manual counts; never invent a default or ask for a quantity. Template contents, auxiliary sheets and the service quantity range are for the backend API to validate, not reasons for a local corrected-file request. Do not independently run a template/content checker to block the original file; explain API-reported business errors when received. Existing file-reading/transport protections and other business and identity checks remain in place. Ask for credentials only upon choosing our product library or when ready for submission. Do not invent detection rules or add unsupported API fields.

Use the current entry or selected-language `package_display_text` as authoritative customer-facing copy. In Chinese, Basic is **Basic：上清表达、抗体表达量（上清抗体浓度）检测和 BLI 两点结合检测。** In English, use these exact options:

- **Basic: Supernatant expression, antibody expression level (supernatant antibody concentration) measurement, and two-point BLI binding analysis.**
- **Standard: Purified antibodies with purity and SPR binding characterization.**
- **Premium: Standard plus thermal stability, polyreactivity, and self-interaction assays.**
- **Customized: Choose the sample type, then select protein property, binding, and developability assays.**

Ask “请选择本次套餐” for `zh` or “Please select a package for this order” for `en`. Do not translate internal `Titer` keys or use the technical selection table to regenerate package wording. Keep `Titer` only for internal mapping.

When our product library is chosen, or before submission in other modes, obtain the customer's JWT: reuse a valid current JWT or use Biointron Account and App Key for the client-side exchange, then use verified `result.token` as `business_token`. Ask only for missing credential values. For library search, use `catalog_auth` from `get_order_input_requirements` when its current question has `credential_check_required`; this includes the server's exchange connection metadata. Its generic `needs_credentials` guidance does not invalidate a JWT already held by the client. Otherwise read `client_side_exchange.url` from a credential response or the metadata already loaded with `order_design(phase="execute", language=language)`. The address comes from `config` / `RUSHDATA_BASE_URL`; never ask the customer to provide an API address. Missing configuration is a service-maintenance problem. User labels `account` and `apkey` map to the API fields `username` and `appkey`. Never use the account, App Key, concatenation or Base64 as `business_token`.

## Server Settings

Prefer the host's native MCP tools. When they are unavailable and a script connection is needed in a full project environment, use the single-call helper `scripts/mcp_client.py` described in [workflow.md](references/workflow.md), not a newly written persistent Node/Python bridge. Bind `business_token` explicitly from the current successful authentication result before a catalog call. Check transport and tool errors before reading structured data; an error object without `content` is not a normal tool result. Never use `content.find` unconditionally, treat a decode failure as an empty catalog, or claim the API/network is faulty without evidence. A dead child process or timed-out request must end the wait, preserve order information and existing choices, and report the confirmed failure stage. Do not automatically retry or promise an invisible connection repair.

The customer-related tools, including catalog search and the local discard instruction, require `business_token`: the current customer's raw JWT, without a `Bearer` prefix. The separate local `get_order_input_requirements` tool needs no business JWT; the MCP connection still uses its service credential. `business_token` does not accept an App Key. If the user supplies an App Key and its bound account instead, follow the client-side credential exchange in `references/workflow.md` before calling business tools. Do not add a `username` argument to MCP tools. `get_report_results(query, business_token)` retrieves experimental results; it is not a saved-design HTML reader and must not be used for the design-view choice.

Send the JWT only in its dedicated MCP argument, never inside `data`, `query`, MCP prompt arguments, files, or diagnostic text. Use the account and App Key only for the exchange request. Keep credentials in invocation memory; do not save, log, or repeat them in replies or generated reports. Client tool history may retain arguments. Missing credentials do not block package explanation or local information collection. Upon choosing our product library, check credentials before its keyword question; otherwise wait until an actual business call is needed. Ask only for missing **Biointron Account**, then **App Key**, and provide the [Biointron website](https://os.biointron.com/). Do not invent an App Key menu or ask ordinary users to locate JWT manually. Reuse an already provided valid JWT without asking again. Never substitute another customer's credentials or assume the server remembers a previous call.

The server uses `RUSHDATA_BASE_URL`, `RUSHDATA_API_TIMEOUT`, `RUSHDATA_DESIGN_TIMEOUT`, and `RUSHDATA_TIME_ZONE`. It sends the supplied token as `X-Access-Token`, separately from MCP authentication. The former `RUSHDATA_ACCESS_TOKEN` and `BIOINTRON_API_AUTH_VALUE` environment variables are ignored. The MCP connection continues to use its own `MCP_ACCESS_TOKEN`.

MCP does not exchange App Keys automatically. The client-side exchange needs an available HTTP or script tool; if neither is available, explain the missing capability and arrange integration support. Do not make manual JWT retrieval the customer's default burden. The standalone `check.py` defaults to `--auth appkey`: design/full modes introduce packages first, then obtain credentials when our product library is chosen, before its keyword input; other modes wait until submission. Biointron Account and App Key use ordinary text input and the exchange address comes from config. Reuse the resulting JWT for later calls. Advanced `--auth jwt` retains hidden JWT input. Neither mode changes MCP authentication.

`RUSHDATA_CONTINUATION_SECRET` must be an independent random server secret of at least 32 characters, different from the MCP access token and customer business tokens. It signs saved-design receipts and must remain on the server.

The active workflow does not require Redis or server-side session storage. The AI carries the signed context between calls; MCP validates it rather than retrieving it by order number. Keep the service signing secret consistent across FC instances.

Set `RUSHDATA_DRAFT_CONTRACT_CONFIRMED=true` only after the backend confirms the antigen and positive-control fields, their encoding, required conditions, and applicable response structures. The setting itself is not evidence of support. Stop design writes while this contract is unresolved; do not remove required data to bypass the check.

Follow `next_action` / `interaction.required_action` to satisfy prerequisites first. Catalog credentials must be available before its keyword/search action. Codex `request_user_input_async` accepts `questions: [{title: "..."}, ...]`; omit `options` for each free-text field. Respect the native tool question limit by splitting a batch locally, without a fresh MCP/model/validation step for each field. Keep asynchronous questions pending until actual answers arrive, then merge the batch and continue the same authorized workflow. Explain all final validation issues in the customer language and use the returned correction batch; never dump raw schema/diagnostics or end with a missing-fields list. Package, source and shipping choices must be real customer choices.

Prefer native free-text entry. If the client's question API requires choices but includes an Other/custom-text box, instruct the user to put the actual value there; any required choices such as “填写此项” or “暂不提供” are UI actions, never usernames, project names or URLs. Selecting an action without supplying the value does not complete the field. Never invent sample account/link choices. Use only a question tool actually exposed and permitted in the current mode; a Plan-only `request_user_input` is not a reason to switch modes or overlook another available native tool. See the independent-field batch example in `references/workflow.md`. Do not search the repository, inspect shell configuration or launch a business runner merely to collect a project name, keyword or path. CLI hosts use their own available question tools or consecutive terminal prompts for the same batch without intermediate validation or MCP/model calls. Only when native questions are genuinely unavailable, explain that limitation and ask one field through text or an interactive terminal, waiting for its answer; MCP cannot force a popup in every client.

For the design workbook, reuse the current order's original attachment when already available; otherwise actually invoke an available file picker. Without file-selection capability, especially in CLI, invoke a native text question or terminal prompt: “请输入本次抗体设计表（.xlsx）的本地文件路径” (`zh`) or “Please enter the local path to the antibody design workbook (.xlsx) for this order” (`en`). Do not stop after a plain “please upload” message. The `read_local_design_workbook` action collects a path for the client to read the original bytes and supply `filename` plus `file_base64`; the path is not itself Base64 or a remote MCP file path. Explain actual file-read or transport-limit failures and reask the same path question. Quantity counting belongs only to actual design execution and never blocks on template/content errors; if no reliable count is available, omit it and pass the unchanged original file to the API. Do not ask the customer to replace a file based on local content or quantity-range checks.

Use the exact customer-facing labels **Biointron Account** and **App Key**. Ask each missing value as a separate ordinary text field when our product library is chosen, or at submission for other modes; never ask for account and key together. App Key does not require masking, hidden input or a separate secure-input dialog. Do not prefill an existing value or repeat it in subsequent replies. The API fields remain `username` and `appkey`. Use server-returned `connection_config` / `catalog_auth`; an absent business API address in client config does not establish missing server configuration. Do not add an API-address question: genuinely missing server configuration belongs to the service operator.

For antigens, ask the source mode first using the selected-language labels in this order: **使用我们的产品库（无需提供链接）** / **Use our product catalog (no link required)** (`SUPPLIER_CATALOG`), **提供外部产品链接** / **Provide an external product link** (`CUSTOMER_URL`), **手动填写已有抗原资料** / **Enter existing antigen information manually** (`MANUAL`). Show only the selected language. Do not replace the product-library option with “provide supplier name and catalog number”. If the customer has already requested our product library, use that mode without asking the source again. If they switch from a product link to our library, update `sourceType` and cancel the pending URL question before collecting the new branch; do not keep asking for the old mode's link.

In **our product-library mode**, first check the current customer's credentials as above, then invoke one native text question or CLI prompt for the antigen keyword, for example CD2. Call `search_order_antigens(keyword, business_token, page_no=1, page_size=50, language=language)`: each call reads its first requested page to establish the page range, then fetches up to four remaining pages concurrently within the same request client. The five-page maximum and deduplication by supplier, catalog number and specification remain unchanged. There is no cross-user credential/result cache or automatic retry. Present `catalog_summary` and the actual returned choices. `total` is the backend's product count; `products_loaded` counts selectable products in this batch, `options_count` counts its specification choices, and `records_loaded` counts the records read. Do not describe a partial batch or its specification count as the entire matching product set. Native dialogs and CLI must offer changing the keyword and, when `has_more=true`, loading more products using the exact returned `next_page`, not the original `page_no+1`. Keep earlier candidates while adding later results. A later-page failure retains already loaded results with a reason and incomplete status; do not retry automatically or claim completion. With no matches, ask for another keyword. Multi-page loading does not prove parity with a webpage using an unverified source or environment.

Preserve all backend search candidates; do not silently reduce them by exact keyword matching, supplier or species. Obtain customer confirmation before applying a filter, explain fuzzy matches when useful, and never treat similarly named products as the same antigen.

A separate product-picker page is not required. Do not ask the customer for a supplier, SKU, link or catalog JSON. Pass the returned `catalog_options` and `catalog_search` alongside `data` to the local input tool; these are selection/navigation context, never design Multipart fields. A selection supplies `supplier`, `catalogNumber`, `specification` and available sample fields. `referenceUrl` is optional for library products: preserve a real returned HTTPS link, never invent one or ask for it when absent. Retain the selected option's verified `cart_data` for the cart stage instead of reconstructing its field mapping.

Only an explicit external-product-link choice collects the customer's actual HTTPS link. Manual-sample mode collects only its required sample details. Do not ask the source mode again once answered. Cart retains its separate link/product-details DTO with no `sourceType`; reuse confirmed product data without guessing undocumented field correspondences. Merge each completed batch, preserving `false`/`0`/`[]`, and follow the next collection action. Perform body validation only at the pre-write checkpoint, then use a correction batch for all discovered issues. Input collection never authorizes order submission.

## Execute

For existing orders that only need submission, start at step 6. Do not request another design file or recreate the orders.

Providing a workbook path only starts file reading and transport checks; quantity counting occurs once in actual design execution, and Excel content acceptance belongs to the API. Once the inputs, current-customer permission preflight and existing design authorization are satisfied, send the following complete user-visible progress message in commentary immediately before `start_order_design`, then continue the call and wait for its result. Show it once per design, not at every stage; it is not a final response or a new confirmation step. The service figures are not delivery promises for this order. Do not invent a duration in minutes or a completion percentage. Do not claim design has started when inputs are missing or preflight failed. Report success or failure truthfully; a saved design is not final order submission, and a long wait or uncertain outcome never authorizes an automatic retry.

> 正在进行订单设计，预计需要较长时间，请耐心等待。

>
> 设计完成后，我会继续反馈结果。

After the answer, call `get_order_input_requirements(stage="design", supplied={"data": <known fields>, "filename": <known filename>, "file_base64": <available original file>}, language=language, mode="collect")`, omitting unknown fields. Resolve sample/source routing choices, then invoke the returned independent question batches. Customized assay choices may use multi-select or customer-entered assay names mapped internally; never ask the customer to write JSON. Do not validate between fields. Missing routing choices remain questions; preserve explicit empty arrays and never invent defaults. Antibody count comes only from the original file at design execution. The product-library branch authenticates before real keyword search; preserve actual candidates and confirmed product data. Do not generate or alter biological sequences.
2. When collection is complete, explicitly call `get_order_input_requirements(stage="design", supplied=<all collected inputs>, language=language, mode="validate")`. Resolve every reported issue through its correction batch and revalidate the completed batch. Once local validation passes and design submission is authorized, establish the current customer. Reuse their valid JWT, or obtain Biointron Account and App Key as separate ordinary text fields and exchange once using the config-provided address. Call `order_design_preflight`; require `hasCompany=true` and a positive `companyId`. Resolve item IDs uniquely from the current catalog; stop on missing or ambiguous matches. A credential/permission failure stops submission, not the preceding package explanation or information collection. Keep the same JWT throughout design-to-cart.
3. Once inputs and permission preflight are ready and the user has authorized design, emit the progress message above, then call `start_order_design` once with the request object, standard Base64 of the original XLSX, and its filename. The file must be nonempty, have an `.xlsx` filename, and be at most 10 MiB. Do not pass a server file path or download address. Omit `data.id` for a new design; for an explicitly requested redesign, use the existing `rushDataServiceId`.
4. After `result_saved` has been verified, complete the **Saved Design Result Choice** below before collecting cart fields or adding to cart. Then call `get_order_input_requirements(stage="cart", supplied={"cart_data": <known cart fields>}, language=language, mode="collect")`. Reuse existing answers and collect independent missing fields as a batch. Before insertion call the same tool with `mode="validate"`; resolve all discovered issues as a correction batch while preserving valid answers. `positiveControl` is optional, and `shippingRequired=false` is a user choice, not a default. Once inputs are ready, saving is confirmed, and cart insertion is authorized, call `add_order_to_cart` once with the complete original `workflow_context`, the same JWT supplied separately as `business_token`, and verified `cart_data`. Follow the current cart contract in the reference; never guess `projectNo` or override receipt identity. This continues the saved design without running design again.
5. Require `status=cart_confirmed` and retain the matching `orderNo`. Use `get_order_cart` for further read-only checks. Never select an order by project name or list position alone.
6. Before final submission, obtain an authoritative quote with `calculate_order_price` and have the customer confirm the exact orders, quote/discount, and readiness of PO and real company information. Missing or unknown prerequisites need human verification; do not invent a PO field or treat `hasCompany`/`canSubmit` as proof of PO validity. Once the customer confirms this submission, call `submit_verified_order` with those same order numbers. It requotes and requires `canSubmit` to be exactly `true` and the quoted order set to match exactly.
7. Report submission acceptance and cart synchronization separately. Explain that accepted orders await Biointron's human confirmation before production; this is not payment, production confirmation or experimental completion. Business-stage names in the reference are not verified API status codes, and cart lookup is not production tracking.

The request uses `projectName`, `catalogNumber`, `antigenCount`, `usingdna`, `sp`, `antigens`, and `positiveControls`; `antibodyProjectCount` is derived from the original workbook when reliably countable, otherwise omitted for API-side validation; it is not a customer input. Customized `testItems` records customer-confirmed arrays for `SAMPLE_TYPE`, `PROTEIN_PROPERTY`, `BINDING` and `DEVELOPABILITY`. Different BLI/FACS/ELISA point variants and both SPR platforms may be selected together when compatible with the sample form. Fixed packages may omit `testItems`. Never invent IDs or silently fill missing custom choices.

The design fields and draft-contract gate above remain distinct from the verified cart JSON contract. Cart `positiveControl` is a single string, not the design's `positiveControls` array. Retain known cart data, but collect missing cart fields only after the saved-design result choice. Confirm `projectNo` from actual design details and validate all required cart fields before cart insertion; stop that insertion if it is missing. `shippingRequired=false` removes an existing address binding, so never select it by default. `true` requires an address already bound through the website; this workflow does not add address binding.

For the standalone `check.py` helper, the terminal entry uses text/choice input for missing file paths, project/antigen fields and order numbers, merges answers, and revalidates. Biointron Account and App Key use ordinary text input; advanced JWT input remains hidden. In `design`/`full`, ask the saved-design result choice after confirmed saving and before missing cart fields. Keep `cart_data` separate at the top level, validate it before cart insertion, and remove it from design Multipart; it is not a nested design field or a new `start_order_design` argument. Interactive answers stay in memory and are not written back to request JSON.

`--non-interactive` forbids all terminal questions, including hidden credential prompts, so missing input/credentials block immediately rather than waiting. Noninteractive `run(args, business_token)` requires explicit `--design-result view` or `--design-result skip` before a design write; an absent preference stops before writing and never defaults to skip. Interactive CLI asks after verified saving. `--design-result-dir` optionally selects the local HTML directory; `--report` remains the JSON workflow outcome, not the HTML artifact. These flags do not supply credentials: programmatic callers still provide the explicit current JWT. There are no plaintext account/key command-line flags or fixed environment JWT fallback. Never use automation flags to guess missing choices or bypass authorization.

`status=ready` means only local input checks passed; it is not execution permission, a valid JWT, confirmed catalog IDs, a saved design, or business success. `start_order_design` and `add_order_to_cart` also return structured `needs_input` when their ordinary input is incomplete, including missing top-level design/cart arguments. Collect the indicated information and continue only the authorized action. Treat authentication/configuration failures and uncertain outcomes after writes separately; never turn them into ordinary missing-field questions or automatic write retries.

If a new project number is assigned only after design saving, obtain it from verified details after the saved-design result choice and before cart insertion. Keep the complete original signed context and the same JWT throughout; do not guess a future project number or recreate the design to collect missing cart metadata.

## Saved Design Result Choice

After this design's `result_saved` is verified, actually invoke one native single-choice card or CLI selection and wait for the customer's answer before collecting cart data or calling `add_order_to_cart`. Use only the current conversation language:

| Language | Question | View choice | Skip choice |
| --- | --- | --- | --- |
| `zh` | 设计已保存，是否查看本次设计结果？ | 需要，查看HTML设计结果 | 不需要，继续下单 |
| `en` | The design has been saved. Would you like to view the design result? | Yes, view the HTML design result | No, continue ordering |

For the view choice, call `get_order_design_result(business_token, workflow_context=workflow_context, language=language)` with the complete original signed context and current JWT. It verifies that context against the exact JWT and saved order, then reads `/order/rushData/report?rushDataServiceId=<signed service ID>` whose response is the actual `report.html` content already extracted by the backend from its result ZIP. On `status=design_result_ready`, save the returned `html` as UTF-8 with BOM (`utf-8-sig`) using the returned `filename`, preserving the HTML content while preventing its retained charset declaration from causing garbled display, and deliver a clickable file link or usable preview before resuming the already-authorized cart workflow. The response includes `orderNo`, `projectName`, `filename=RushData_Design_<safe order>.html`, `mime_type="text/html"`, `report_type="design"`, `write_performed=false` and the complete unchanged `workflow_context`. A success statement, raw HTML code or login-page URL is not delivery. The skip choice performs no design-result retrieval or HTML rendering and immediately resumes that same authorized workflow. Neither choice requires another general continue confirmation or grants final-submit consent; retain the existing exact-order/quote confirmation before final submission.

Use the dedicated saved-design reader; do not invent download endpoints or URLs. `/inspectionReportHtml` and `get_report_results` concern experimental reports and must not replace the design result; neither may an order receipt or order number. If retrieval, rendering or delivery fails, explain the confirmed reason, preserve the saved order, then invoke one choice: “重试读取设计结果” / “继续下单” for `zh`, or “Retry reading the design result” / “Continue ordering” for `en`. After an explicit retry choice, retry only the failed step: repeat the read request only for an actual read failure, and reuse the already-returned HTML for local save or delivery failures. Do not automatically retry or run design again. A continue choice resumes the existing authorized cart workflow.

Keep the complete signed `workflow_context` and exact current JWT unchanged throughout this choice, HTML delivery and recovery. Store the choice and delivery status only in outer client state, never in business data or the signed object. `workflow_context.next_tool="add_order_to_cart"` identifies the eventual write continuation, not permission to skip the view choice. Preserve a pending choice or failed delivery across handoffs; do not repeat an answered choice or treat HTML failure as design failure.

## Preserve Context and Continue

Successful design saving returns the complete object `workflow_context={version:1, order_no, expires_at, next_tool:"add_order_to_cart", continuation_token:<full signed string>}`. The top-level `continuation_token` is temporarily retained for compatibility. Prefer returning the entire unchanged `workflow_context` to `add_order_to_cart`; keep the JWT in the separate `business_token` argument. If a context, receipt, or order number is supplied together with another representation, all must agree. An order number alone cannot recover a missing receipt.

**When organizing context, compacting memory, or handing off to another chat/agent, retain the complete `workflow_context` verbatim. Never truncate the signature, summarize the object instead of copying it, or reconstruct it from an order number.** Maintain a separate private handoff record per secure customer-credential reference and `order_no`. Also retain the last confirmed stage, confirmed `cart_data` including real `false`/`0` values, outstanding fields, the user's authorized scope, the last tool call, and any uncertain outcome. Keep these phase/cart/authorization notes in the outer handoff record, never as extra fields in `workflow_context`. This is a Skill/client preservation requirement, not a guarantee that every client retains history; if context is lost, stop because the server has no copy. Reuse supplied information rather than asking again.

JWTs and App Keys must not appear in ordinary summaries, shareable documents, repository memory, or server-side storage. Use a secure credential reference in the handoff; do not write real receipts into repository memory either. If the original JWT is unavailable, request secure access to it. A newly obtained different JWT cannot continue the old signed context; it may only support authorized read-only checks. Preserve the signed context in private client continuity, not in public output.

The credential is valid for at most one hour and is bound to the exact JWT and API environment. This is credential validity, not a server-cache TTL. MCP verifies the signature, expiry, identity and matching order details/`projectNo`; missing main `orderId` cannot be replaced by a service ID. Before cart insertion, details must identify draft (`-3`) or cart (`00`) status; submitted or unknown statuses are blocked. This read-only check is not atomic. Lost or expired proof cannot be reissued from the order number or a detail lookup. `designStatus=ok` or calculation completion alone cannot replace saved SSE evidence. Never redesign merely to recover lost proof.

After confirmed cart success, stop using and discard the local continuation context while retaining the order number and confirmed outcome. On an explicit request to end/cancel continuation, call `end_order_workflow` with the order, JWT and original context/receipt. Its `status="discard_context"`, `server_revoked=false`, `client_action="delete_local_context"`, and `business_order_cancelled=false` instruct the AI to discard the local context only. The service cannot revoke already issued signatures or erase other copies, and it does not cancel/delete an actual order or cart item.

There are no Redis claims or shared deduplication guarantees. Sequential cart calls first check the cart read-only; an existing order returns `already_in_cart=true`, `write_performed=false`, and `cart_data_applied=false`. Do not claim that newly supplied antigen or shipping fields were applied; cross-FC concurrent writes or identical design requests are not strictly deduplicated. Backend idempotence is required for that guarantee. Do not auto-retry or concurrently write the same order. If a result is uncertain, preserve the stage and identity and check `get_order_cart` first. An explicitly authorized redesign must discard the local old context, but MCP cannot invalidate other copies or prove the current saved design version from details alone.

When MCP is connected, do not automatically fall back to CLI or website operations after a failure. The standalone `check.py` calls the business API directly; use it only when explicitly requested, following its original authorization and uncertainty rules. Missing/invalid input remains `needs_input`; authentication, invalid proof or uncertain write results are not ordinary form-completion cases.
